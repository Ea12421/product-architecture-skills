# 产品架构搭建 Skill

## 1. 这个 skill 是什么

帮用户从 0 搭建 AI 产品的整体架构。产出是产品经理站在业务视角画的全局蓝图——业务模块怎么划分、模块间如何协作、数据如何流转——而不是 UI 设计或代码实现。

核心交付物有两个路径(由用户在开场 5 问中选择):
- **路径 A**:仅产品架构图 + PRD 要点
- **路径 B**:完整 5 部分立项方案

不同公司场景(中大型 / 小公司创业 / 个人项目)会影响这两个路径的**语气和深度**,但都能用。

## 2. 何时触发 / 何时不触发

**何时触发**(明确表达以下意图):
- 想搭建/设计一个 AI 产品的架构
- 想画 4 层架构图(数据/能力/场景/触达)
- 想撰写 AI 产品的立项方案/项目方案
- 想从 0 到 1 把一个产品的整体结构想清楚

**何时不触发**:
- UI/UX 设计、页面交互、视觉风格(属于信息架构)
- 单纯写 PRD(用户没明确要求架构图或立项方案)
- 技术栈选型、代码实现、部署方案(属于技术架构)
- 早期需求探索 / 功能 brainstorm(用户还没想清楚)
- 单个功能模块的设计(产品架构是全局视角)
- 想分析/拆解已有产品(用 `product-architecture-teardown` skill)

## 3. 核心概念

### 3.1 产品架构是什么

**定义**:产品架构 = 把一个产品拆成几大业务模块 + 说明这些模块如何协作 + 标注数据如何在模块间流转。

不是"这个产品长什么样"(UI),也不是"用什么技术做"(技术架构),而是"由哪几块业务组成、相互怎么搭配、数据从哪进哪出"。

| 视角 | 看到的微信 | 给谁看 |
|------|-----------|--------|
| 信息架构 | 底部 4 个 tab | 交互设计师 |
| **产品架构** ★ | 六大业务模块:IM / 社交 / 内容 / 支付 / 平台 / 企业服务 | 老板和团队 |
| 技术架构 | 分布式 / PaxosStore / 微服务 | CTO / 架构师 |

**本 skill 只处理中间那个。** 如果用户问的其实是别的架构("页面跳转怎么设计" = 信息架构、"用什么数据库" = 技术架构),明确指出并建议用户问对应的工具/人,不要硬塞。

### 3.2 4 层最小骨架

| 层 | 回答的问题 |
|---|----------|
| 数据层 | 数据/资源从哪来? |
| 能力层 | 拿数据做什么处理? |
| 场景层 | 能力怎么组合成场景? |
| 触达层 | 结果怎么交付给用户? |

原则:
- 层名不固定,固定的是"下层为上层支撑"的分层原则
- 4 层是下限,复杂产品可扩展到 5-6 层
- 必须有跨层数据流转箭头——少了流转就不是架构,是功能清单

### 3.3 数据流转的两种必备类型

每张架构图必须至少包含:
- **沉淀流**:用户行为/对话/上传 → 数据层(例:聊天记录沉淀进对话库)
- **回补流**:数据层加工后 → 上层(例:优质问答回补到知识库)

可选追加:跨系统外延流(如工单 → CRM)、反向回路流。

## 4. 工作流

### Step 1:开场 5 问

用纯文字依次询问。如果用户首句已经回答了某个问题,跳过对应问题。

**问题 1:你要搭建的产品是什么?** 用一句话描述(面向谁 + 解决什么)。

**问题 2:你的场景是?(单选,决定语气和深度)**
1. 中大型公司(有完整技术/算法/数据团队,只负责产品视角)
2. 小公司/创业团队(需向管理层争取资源)
3. 个人/学习/探索项目(无需对外汇报)

**问题 3:交付物范围?(单选,决定路径)**
1. 仅产品架构图
2. 完整立项方案(含技术选型 + 成本 + 实施计划)
3. 两者都要

**问题 4:产出形态?(可多选)**
1. 文字结构化说明
2. Mermaid 架构图代码
3. HTML 可视化(带可编辑文字 + 下载按钮)

**问题 5:视觉风格?(仅当问题 4 选了 HTML 时询问;单选)**
1. 技术克制(默认推荐)
2. 暖色友好
3. 极简日式
4. 暗黑赛博

未明确选择默认走 1(技术克制)。具体色板和字体规则见 `references/visual-styles.md`。

### Step 2:资料盘点

评估手头信息充足度:

- **充足**:用户描述清楚 + Claude 对产品类型有足够认知 → 进 Step 3
- **中等**:信息零散 → 调用 web search(若环境支持联网)搜同类产品常见架构作为参考 → 进 Step 3
- **稀缺**:信息严重不足 / 无联网 / 冷门垂直领域 → 进补料分支:

> 我需要再了解几件事才能给你可靠的架构建议:
> 1. 目标用户大概是什么群体?
> 2. 和现有解决方案相比,差异点在哪?
> 3. 是 ToC 还是 ToB?

用户拒绝补料 → 明确告知:"当前信息不足以给出可靠架构,建议先想清楚以上几点再来。" **不要硬出全推测的架构图。**

### Step 3:路径分流

| 问题 3 | 路径 |
|---|---|
| 1(仅架构图) | 路径 A:架构图 + PRD 要点 |
| 2(完整立项方案) | 路径 B:5 部分立项方案 |
| 3(两者都要) | 路径 B(第二部分包含架构图,自动覆盖 A) |

### 路径 A:产品架构图 + PRD 要点

回答以下 5 个问题,逐层填出 4 层骨架:

1. 数据从哪来? → 数据层
2. 拿数据做什么处理? → 能力层
3. 能力怎么组合成场景? → 场景层
4. 结果怎么交付给用户? → 触达层
5. 数据怎么流转? → 至少 1 条沉淀流 + 1 条回补流

附加 PRD 要点(**根据问题 2 调整深度**):

| 问题 2 场景 | PRD 要点处理 |
|---|---|
| 中大公司 | 简略:目标用户 + 核心场景 + MVP 功能优先级(团队会细化) |
| 小公司/创业 | 详细:加端到端流程一句话 + P0/P1/P2 分级 + 关键指标 |
| 个人/学习 | 加"为什么这么分"的设计解释维度(学习/复盘视角) |

### 路径 B:完整 5 部分立项方案

按以下顺序产出。**路径 B 在不同场景下的语气框架不同**:

| 问题 2 场景 | 立项方案的框架定位 |
|---|---|
| 中大公司 | 内部 review 框架:跨部门协作、上线节奏、与现有产品矩阵的关系 |
| 小公司/创业 | 争取资源框架:ROI、回本周期、风险与退出机制 |
| 个人/学习 | 自我推演框架:技术可行性、自费成本、个人时间投入、是否值得做 |

**5 部分内容**:

1. **业务背景与需求**:项目源起 + 项目目标(量化 + 时间)+ 目标用户画像 + 典型场景 3-5 个 + 竞品参考与差异化
2. **产品架构**:4 层架构图(含至少 2 条数据流转)+ 每层具体内容和理由 + 跨层流转的设计意图
3. **核心链路与功能清单**:端到端流程图(节点 + 负责方 + 技术要求)+ MVP 功能 P0/P1/P2 + 前后端分工表
4. **技术选型与成本**(执行前必先反问合规,见下)
5. **实施计划**:分期规划 + 团队配置(角色 + 人数 + 职责)+ 风险与应对(3-5 条)+ 退出机制

**第四部分执行前必须反问合规**:

> "在给技术选型建议前我需要确认一件事:你的业务有没有数据合规硬性要求?比如用户身份证、银行卡、医疗记录、政府数据等不能传到第三方服务器的限制。"

- 有合规要求 → 跳过商用 API 推荐,直接走开源私有化方案,明确说明合规约束
- 无合规要求 → 推荐第一阶段商用 API + 普通云服务器路线

三个维度:模型选型 / 算力方案 / 数据来源。

⚠️ 涉及具体定价(API、云服务器、GPU 月租等)**必须用最新数据**:
- 有联网 → 调用 web search 获取当前价格,**不使用任何旧数字**
- 无联网 → 明确告知:"具体定价需要实时数据,建议你访问 DeepSeek、阿里云百炼、火山引擎等官网确认最新报价。"

成本汇总:一次性投入 / 月运营成本 / ROI 测算 / 回本周期。**按问题 2 场景调整**:中大公司用部门预算视角、小公司/创业用现金流/Burn rate 视角、个人用自费视角。

## 5. 强制规则

1. **数据流转必须有**:至少 1 条沉淀流 + 1 条回补流。实在想不到时明确告知"当前阶段尚未识别到数据回流路径,建议设计后期回路"。**不允许跳过。**
2. **4 层是起点不是终点**:平台型加生态层 / 多 Agent 型分工具层 / ToB 加安全层。底线不少于 4 层。
3. **定价用最新数据**:涉及成本时强制 web search,不能联网时明确告知用户自查(无任何内置旧定价)。
4. **架构 ≠ 产品起点**:用户表现"还在 brainstorm 阶段、需求都没想清楚"时,主动指出:"你这个阶段需要的不是架构图,是先把需求和核心链路想清楚、跑通 MVP。产品架构是复杂度增长后或对外汇报时才画的整理动作,不是起点。" 让用户自己判断是否继续。

## 6. 跨 skill 协作 + 中途偏离 + 收尾

### 检测「参考已有产品」时的反问

用户的话里出现「参考 XX」「类似 XX」「借鉴 XX」「像 XX 那样」等词,先反问:

> "你是想直接基于你的设想搭建,还是想先分析下参考产品的架构再搭?"

- 选直接搭 → 继续当前 skill
- 选先分析参考产品 → 提示:"建议先用 `product-architecture-teardown` skill 分析参考产品。如果你没装,也可以直接告诉我参考产品的关键信息,我在搭建过程中顺手做轻量拆解作为参考。"

### 中途偏离

用户切换话题时:
1. 识别偏离
2. 总结当前进度:"我们暂停在 [当前步骤]。已收集:[列已确认项]。要切换是吧?"
3. 干净交接,等确认后退出 skill
4. 保留 2-3 行摘要,方便用户续接

### 收尾行为

| 情况 | 行为 |
|---|---|
| 完整产出 | 直接结束,不追加 |
| 带假设的部分产出(用户拒绝补料 / `[推测]` 标记) | 追加:"产出中带 [推测] 标记的部分是基于假设。如果之后你拿到准确信息想完善,把信息贴给我即可重跑。" |
| 中途叫停 | 追加:"我们暂停在 [XX 步骤],已收集:……。要继续时把这段贴回来就能接着跑。" |

## 7. 产出形态

按问题 4 的多选结果产出。

### 文字结构化说明(默认)

按 4 层骨架逐层说明,最后写"数据流转"独立小节列出所有流转方向和内容。

### Mermaid 架构图代码

用 `graph TB` 画分层,`subgraph` 圈每层。⚠️ Mermaid 对"分层堆叠 + 跨层箭头"的可视化表现一般,节点多时容易乱。视觉要求高建议同时选 HTML。

### HTML 可视化(带可编辑文字 + 下载按钮)

⚠️ **如果用户选了 HTML 输出,立即按 §8 引用规则表的顺序读 references**:
1. **先读** `references/visual-styles.md`(决定色板和字体)
2. **再读** `references/html-spec.md`(布局 / 工具栏 / 模块 / 缩放 / 可编辑 / 下载)
3. **画箭头前读** `references/arrow-routing.md`(间隙列路由 + 垂直起终点 + 添加/删除交互)

每读完一份 reference,在产出前用一句话向自己确认"已阅读 X.md,关键约束是 Y"——见 §8 自我确认机制。

## 8. ⚠️ 引用规则(必须遵守)

下面每条规则在触发条件成立时**必须**先读对应 reference,再继续产出。**不读直接产出 = 错误产出。**

| 触发条件 | 必读 reference | 读取时机 |
|---|---|---|
| Q4 选择了 HTML 输出 | `references/visual-styles.md` | 决定色板和字体之前 |
| Q4 选了 HTML(visual-styles.md 已读) | `references/html-spec.md` | 写任何 HTML/CSS 之前 |
| 画自动箭头 / 处理「添加连接」/「删除箭头」 | `references/arrow-routing.md` | 写任何 SVG path 之前 |

**自我确认机制**:读完每份 reference,在产出前用一句话向自己确认:
> "已阅读 [文件名],关键约束是 [一句话总结]。"

未做自我确认 = 视为未读,必须重读。

## 9. 通用自检(产出前过一遍)

- [ ] 已按问题 3 的选择走对路径(A 仅架构图 / B 完整立项方案)
- [ ] 有至少 1 条沉淀流 + 1 条回补流(或明确告知缺失原因)
- [ ] PRD 要点 / 立项方案的语气框架按问题 2 调整了(中大公司 / 小公司创业 / 个人)
- [ ] 路径 B 第四部分执行前问了合规问题
- [ ] 涉及具体定价时用了 web search 或明确告知用户自查
- [ ] 用户拒绝补料时没有硬出全推测的架构图
- [ ] 没把 UI 评测 / 技术架构 / 单功能设计硬塞进产出
- [ ] HTML 产出时引用规则表里相关 reference 都读了 + 做了自我确认

> ⚠️ HTML 专项自检(工具栏 fixed、间隙列路由、可编辑、下载等)在 `references/html-spec.md` 和 `references/arrow-routing.md` 各自的自检节里,不在主 SKILL.md 重复。

## 10. 示例

### 示例 1:场景 1 + 仅架构图(路径 A)

**用户**:「帮我搭建一个面向制造业的 AI 售后客服的产品架构。」

**Claude**:开场 5 问(Q1 已答)→ Q2 选 1(中大公司)→ Q3 选 1(仅架构图)→ Q4 选 1 + 2(文字 + Mermaid)。资料充足 → 路径 A(中大公司语气:PRD 要点简略)。

**产出**:数据层(产品手册、售后 FAQ、维修工单、用户对话)/ 能力层(大模型对话、RAG、意图识别、工单对接)/ 场景层(智能问答、智能报修、人工兜底、满意度回访)/ 触达层(微信公众号、官网、App)。数据流转:沉淀流(用户对话 → 对话库)/ 回补流(优质问答 → 知识库)/ 外延流(报修工单 → CRM)。PRD 要点简略版 + 对应 Mermaid 代码。

### 示例 2:场景 2 + 完整立项方案 + HTML(路径 B)

**用户**:「我要做一个 AI 售后客服,需要完整方案给老板审批。」

**Claude**:Q2 选 2(小公司/创业)→ Q3 选 2(完整立项方案)→ Q4 选 1 + 3(文字 + HTML)→ Q5 选 1。资料充足 → 路径 B(争取资源框架)。

**Claude**:
- 触发 HTML → **立即读** visual-styles.md → 自我确认"已阅读 visual-styles.md,本次风格 1 技术克制,主色 #3B82F6,圆角 8px" → **读** html-spec.md → 自我确认 → **画箭头前读** arrow-routing.md → 自我确认
- 第四部分执行前先反问合规 → 无合规要求 → 联网搜 DeepSeek-V4 API 和阿里云 ECS 当前价格 → 填入第四部分
- 完整 5 部分立项方案,重点放 ROI / 回本周期 / 退出机制
- HTML 可视化呈现 4 层架构图(60px 工具栏 + 左侧 80px 标签 + 模块 pill + 自动箭头走间隙列 + 可编辑文字 + 下载按钮)
