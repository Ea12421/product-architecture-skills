# 产品架构搭建 Skill

## 1. 这个 skill 是什么

帮用户从 0 搭建 AI 产品的整体架构。产出是产品经理站在业务视角画的全局蓝图——业务模块怎么划分、模块间如何协作、数据如何流转——而不是 UI 设计或代码实现。

核心交付物有两个路径（由用户在开场 4 问中选择）：
- 仅产品架构图 + PRD 要点（路径 A）
- 完整 5 部分立项方案（路径 B）

不同公司场景（中大型 / 小公司创业 / 个人项目）会影响这两个路径的**语气和深度**，但都能用。

## 2. 何时触发

仅在用户明确表达以下意图时启动：
- 想搭建/设计一个 AI 产品的架构
- 想画 4 层架构图（数据/能力/场景/触达）
- 想撰写 AI 产品的立项方案/项目方案
- 想从 0 到 1 把一个产品的整体结构想清楚

## 3. 何时不触发

下列场景不要触发这个 skill：
- UI/UX 设计、页面交互、视觉风格（属于信息架构）
- 单纯写 PRD（用户没明确要求架构图或立项方案）
- 技术栈选型、代码实现、部署方案（属于技术架构）
- 早期需求探索 / 功能 brainstorm（用户还没想清楚要做什么）
- 单个功能模块的设计（产品架构是整个产品的全局视角）
- 想分析/拆解已有产品（用 product-architecture-teardown skill）

## 4. 核心概念

### 4.1 产品架构是什么

**定义**：产品架构 = 把一个产品拆成几大业务模块 + 说明这些模块如何协作 + 标注数据如何在模块间流转。

简单说：不是"这个产品长什么样"（那是 UI），也不是"这个产品用什么技术做"（那是技术架构），而是"这个产品由哪几块业务组成、相互怎么搭配、数据从哪进哪出"。

**举个例子（微信）**：

| 视角 | 看到的微信 | 给谁看 |
|------|-----------|--------|
| 信息架构 | 底部 4 个 tab：消息 / 通讯录 / 发现 / 我 | 交互设计师 |
| **产品架构** ★ | 六大业务模块：IM 通讯 / 社交网络 / 内容生态 / 金融支付 / 平台生态 / 企业服务（+ 底层：账号体系 / 关系链 / 消息系统） | 老板和团队 |
| 技术架构 | 分布式系统 / PaxosStore / 微服务 / Raft 协议 | CTO / 架构师 |

同一个微信，三个视角看到完全不同的东西。**本 skill 只处理中间那个产品架构。**

### 4.1.1 别和其他架构搞混

| 架构类型 | 回答什么问题 | 谁主导 |
|---------|------------|--------|
| 信息架构 | 用户看到什么？页面怎么组织？导航怎么分级？ | 产品/交互设计师 |
| **产品架构** ★ | 产品由哪几块业务组成？模块间怎么协作？数据怎么流转？ | **产品经理（本 skill）** |
| 技术架构 | 系统怎么实现？技术栈？部署？ | CTO / 架构师 |

如果用户问的其实是别的架构（比如"页面跳转怎么设计" = 信息架构、"用什么数据库" = 技术架构），明确指出并建议用户问对应的工具/人，不要在产品架构 skill 里硬塞。

### 4.2 4 层最小骨架

从下往上：

| 层 | 回答的问题 | 内容 |
|---|----------|------|
| 数据层 | 数据/资源从哪来？ | 用户数据、知识库、第三方接入等 |
| 能力层 | 拿数据做什么处理？ | 大模型、RAG、推理、生成 |
| 场景层 | 能力怎么组合成场景？ | 把能力封装成具体业务场景 |
| 触达层 | 结果怎么交付给用户？ | App、Web、小程序、API 等 |

原则：
- 层名不固定，固定的是"下层为上层支撑"的分层原则
- 4 层是下限，复杂产品可扩展到 5-6 层
- 必须有跨层数据流转箭头——少了流转就不是架构，是功能清单

### 4.3 数据流转的两种必备类型

每张架构图必须至少包含：
- **沉淀流**：用户行为/对话/上传 → 数据层（例：聊天记录沉淀进对话库）
- **回补流**：数据层加工后 → 上层（例：优质问答回补到知识库）

可选追加：跨系统外延流（如工单 → CRM）、反向回路流。

## 5. 工作流

### Step 1：开场 4 问

用纯文字依次询问。如果用户首句已经回答了某个问题，跳过对应问题。

**问题 1：你要搭建的产品是什么？**
请用一句话描述（面向谁 + 解决什么）。例如：
- "面向制造业的 AI 售后客服"
- "帮律师起草合同的 AI 助手"
- "企业内部的设备检修智能体"

**问题 2：你的场景是？（单选，决定语气和深度）**
1. 中大型公司（有完整技术/算法/数据团队，你只负责产品视角）
2. 小公司/创业团队（需向管理层争取资源）
3. 个人/学习/探索项目（无需对外汇报）

**问题 3：交付物范围？（单选,决定路径）**
1. 仅产品架构图
2. 完整立项方案（含技术选型 + 成本 + 实施计划）
3. 两者都要

**问题 4：产出形态？（可多选）**
1. 文字结构化说明
2. Mermaid 架构图代码
3. HTML 可视化（带可编辑文字 + 下载按钮）

### Step 2：资料盘点

评估手头信息充足度：

- **充足**：用户描述清楚 + Claude 对产品类型有足够认知 → 进 Step 3
- **中等**：信息零散 → 调用 web search（若环境支持联网）搜同类产品的常见架构作为参考 → 进 Step 3
- **稀缺**：信息严重不足 / 无联网 / 冷门垂直领域 → 进"补料分支"：

  > 我需要再了解几件事才能给你可靠的架构建议：
  > 1. 目标用户大概是什么群体？
  > 2. 和现有解决方案相比，差异点在哪？
  > 3. 是 ToC 还是 ToB？

  用户补完信息后再进 Step 3。如果用户拒绝补料，明确告知："当前信息不足以给出可靠架构，建议先想清楚以上几点再来。" **不要硬出一个全是猜测的架构图。**

### Step 3：路径分流

根据问题 3 的答案选择路径，问题 2 的答案影响路径内的语气和深度：

| 问题 3 | 路径 |
|--------|------|
| 1（仅架构图） | 路径 A：架构图 + PRD 要点 |
| 2（完整立项方案） | 路径 B：5 部分立项方案 |
| 3（两者都要） | 路径 B（5 部分立项方案的第二部分就包含架构图，自动覆盖 A）|

### 路径 A：产品架构图 + PRD 要点

回答以下 5 个问题，逐层填出 4 层骨架：

1. 数据从哪来？→ 数据层
2. 拿数据做什么处理？→ 能力层
3. 能力怎么组合成场景？→ 场景层
4. 结果怎么交付给用户？→ 触达层
5. 数据怎么流转？→ 至少 1 条沉淀流 + 1 条回补流

附加 PRD 要点（**根据问题 2 调整深度**）：

| 问题 2 场景 | PRD 要点处理 |
|------------|------------|
| 中大公司 | 简略写：目标用户 + 核心场景 + MVP 功能优先级（团队会细化）|
| 小公司/创业 | 详细写：加端到端流程一句话 + P0/P1/P2 分级 + 关键指标 |
| 个人/学习 | 加"为什么这么分"的设计解释维度（学习/复盘视角）|

### 路径 B：完整 5 部分立项方案

按以下顺序产出。**路径 B 在不同场景下的语气框架不同**：

| 问题 2 场景 | 立项方案的框架定位 |
|------------|------------------|
| 中大公司 | 内部 review 框架：重点放在跨部门协作、上线节奏、与现有产品矩阵的关系 |
| 小公司/创业 | 争取资源框架：重点放在 ROI、回本周期、风险与退出机制（争取老板/投资人批准）|
| 个人/学习 | 自我推演框架：重点放在技术可行性、自费成本、个人时间投入、是否值得做（给自己看的决策依据）|

5 部分内容：

**第一部分：业务背景与需求**
- 企业现状 / 项目源起（中大：业务现状；小公司：市场机会；个人：个人动机）
- 项目目标（量化指标 + 验收时间）
- 目标用户画像
- 典型使用场景 3-5 个
- 竞品参考与差异化优势

**第二部分：产品架构**
- 4 层架构图（含至少 2 条数据流转）
- 每层具体内容和理由
- 跨层流转的设计意图

**第三部分：核心链路与功能清单**
- 端到端流程图（节点 + 负责方 + 技术要求）
- MVP 功能 P0/P1/P2 清单
- 前后端分工表

**第四部分：技术选型与成本**

⚠️ 执行前必须先反问：

> "在给技术选型建议前我需要确认一件事：你的业务有没有数据合规硬性要求？比如用户身份证、银行卡、医疗记录、政府数据等不能传到第三方服务器的限制。"

- 有合规要求 → 跳过商用 API 推荐，直接走开源私有化方案，明确说明合规约束
- 无合规要求 → 推荐第一阶段商用 API + 普通云服务器路线

三个维度：
1. 模型选型：商用 API / 开源私有化部署 / 开源 + 微调（三方案对比）
2. 算力方案：API 场景几乎零算力 / 私有化按模型规模选 GPU
3. 数据来源:企业存量文档 + FAQ + 工单历史 / 运营积累用户对话 / 合成数据

⚠️ 涉及具体定价（API 价、云服务器、GPU 月租等）必须用最新数据：
- 有联网能力 → 调用 web search 获取当前价格，**不使用任何旧数字**
- 无联网 → 明确告知："具体定价需要实时数据，建议你访问 DeepSeek、阿里云百炼、火山引擎等官网确认最新报价。"

成本汇总：一次性投入 / 月运营成本 / ROI 测算 / 回本周期。

**根据问题 2 场景调整成本视角**：
- 中大公司：用公司预算视角（部门预算、跨季度规划）
- 小公司/创业：用现实约束视角（现金流、Burn rate、回本压力）
- 个人/学习：用自费视角（个人能承受的月支出、副业 ROI、时间成本）

**第五部分：实施计划**
- 分期规划与排期
- 团队配置（角色 + 人数 + 职责）—— 个人场景这部分简化为"我自己 + 可能的外包/合作"
- 风险与应对（至少 3-5 条）
- 退出机制（什么情况放弃 + 沉没成本评估）

## 6. 强制规则

### 规则 1：数据流转必须有

任何架构图必须至少包含：
- 1 条沉淀流（用户行为 → 数据层）
- 1 条回补流（数据层 → 上层）

实在想不到回路时明确告知："当前阶段尚未识别到数据回流路径，建议设计后期回路。" **不允许跳过。**

### 规则 2：4 层是起点不是终点

默认 4 层，但允许并鼓励扩展：
- 平台/marketplace 型 → 加生态层
- 多 Agent 协同型 → 能力层内部分"工具层 / Agent 编排层"
- ToB 企业级 → 加纵向贯穿的"安全/权限层"

底线：不能少于 4 层。

### 规则 3：定价用最新数据

不使用任何内置的旧定价。涉及成本时强制 web search；不能联网时明确告知用户自查。

### 规则 4：架构 ≠ 产品起点

如果用户表现出"还在 brainstorm 阶段、需求都没想清楚"，主动指出：

> "你这个阶段需要的不是架构图，是先把需求和核心链路想清楚、跑通 MVP。产品架构是复杂度增长后或对外汇报时才画的整理动作，不是产品的起点。你确定现在是合适的时机吗？"

让用户自己判断是否继续。

## 7. 跨 skill 协作

### 检测「参考已有产品」时的反问

如果用户的话里出现「参考 XX」「类似 XX」「借鉴 XX」「像 XX 那样」等词，先反问：

> "你是想直接基于你的设想搭建，还是想先分析下参考产品的架构再搭？"

- 选直接搭 → 继续当前 skill
- 选先分析参考产品 → 提示：
  > "建议先用 product-architecture-teardown skill 分析参考产品。如果你没装这个 skill，也可以直接告诉我参考产品的关键信息（核心功能、目标用户、数据来源），我在搭建过程中顺手做轻量拆解作为参考。"

## 8. 中途偏离处理

如果用户在工作流中途切换话题（比如开场 4 问还没答完突然说"等等，你先帮我看个文档"），按以下流程：

1. **识别偏离**：用户的话和当前 skill 工作流明显无关
2. **总结当前进度**：
   > "我们暂停在 [当前步骤]。已收集的信息：[列出已确认的项]。要切换是吧？"
3. **干净交接**：等用户确认切换后退出 skill，让 Claude 处理新方向
4. **保留摘要**：退出前把已收集的信息整理成 2-3 行摘要，方便用户之后续接

不要强制要求用户完成 skill 后再切换。

## 9. 收尾行为

根据情况决定是否追加：

| 情况 | 行为 |
|------|------|
| 完整产出（信息齐全、按路径走完） | 直接结束，不追加任何"要不要…"的话 |
| 带假设的部分产出（用户拒绝补料、含 `[推测]` 标记） | 追加："产出中带 [推测] 标记的部分是基于假设。如果之后你拿到准确信息想完善，把信息贴给我即可重跑。" |
| 中途叫停（用户中断退出） | 追加："我们暂停在 [XX 步骤]，已收集的信息：……。要继续时把这段贴回来就能接着跑。" |

## 10. 产出形态

按问题 4 的多选结果产出。多选时按以下顺序：

### 文字结构化说明（默认）

按 4 层骨架逐层说明，最后写"数据流转"独立小节列出所有流转方向和内容。

### Mermaid 架构图代码

用 `graph TB` 画分层，`subgraph` 圈每层，节点写内容，箭头标流转方向和文字标签。

⚠️ Mermaid 对"分层堆叠 + 跨层箭头"的可视化表现一般，节点多时容易乱。如果用户对视觉效果要求高，建议同时选 HTML 可视化。

### HTML 可视化（带可编辑文字 + 下载按钮）

产出一段完整的、独立可运行的 HTML 代码：

**视觉要求**：
- 4 层堆叠布局（CSS Grid 或 Flexbox 实现）
- 每层不同颜色区分（自下而上：数据/能力/场景/触达 用不同色块）
- 跨层箭头用 SVG 或 CSS 伪元素绘制
- 必须包含数据流转箭头标注（沉淀流 + 回补流）

**可编辑要求**：
- 所有文字元素加 `contenteditable="true"` 属性：层名、模块名、数据流转标签都可以在浏览器里直接点击编辑
- 文字元素 hover 时给一个浅色背景提示用户可编辑
- 编辑只在浏览器里临时生效，关闭页面会丢失（除非用下载按钮）

**下载按钮要求**：
- 页面顶部或角落固定一个「下载修改后版本」按钮
- 用户编辑后点击 → JavaScript 用 Blob + URL.createObjectURL 把当前 DOM 序列化成 HTML 字符串 → 触发浏览器下载完整的 .html 文件
- 文件名格式：`产品架构_[产品名]_[时间戳].html`

**适配两种环境**：
- 在 claude.ai 里：作为 artifact 渲染，用户直接编辑、点下载按钮即可
- 在 Claude Code / Codex 等环境里：把完整 HTML 代码贴给用户，告诉用户"保存为 .html 文件后用浏览器打开即可编辑和下载"

## 11. 示例

### 示例 1：场景 1 + 仅架构图（路径 A）

**用户**：「帮我搭建一个面向制造业的 AI 售后客服的产品架构。」

**Claude**：触发 skill，开场 4 问（问题 1 已答，跳过）：
- 问题 2 → 用户选 1（中大公司）
- 问题 3 → 用户选 1（仅架构图）
- 问题 4 → 用户选 1 + 2（文字 + Mermaid）

**Claude**：资料盘点 = 充足 → 路径 A（中大公司语气：PRD 要点简略）。

**产出（节选）**：

```
数据层：产品手册、售后 FAQ、维修工单历史、用户对话记录
能力层：大模型对话、RAG 知识库检索、意图识别、工单系统对接
场景层：智能问答、智能报修、人工兜底、满意度回访
触达层：微信公众号、公司官网、App 内嵌

数据流转：
- ↓ 沉淀流：用户对话 → 对话数据库
- ↑ 回补流：优质问答 → 知识库
- ↗ 外延流：报修工单 → 公司 CRM

PRD 要点（简略版）：
- 目标用户：已购买产品的终端消费者
- 核心场景：售后咨询 / 故障报修 / 投诉处理
- MVP 功能：P0 文本对话+RAG / P0 意图识别 / P0 人工转接 / P1 智能报修
```

加上对应的 Mermaid 代码块。

### 示例 2：场景 2 + 完整立项方案（路径 B）

**用户**：「我是公司里唯一懂 AI 的产品经理，要做一个 AI 售后客服，需要完整方案给老板审批。」

**Claude**：触发 skill → 问题 2 选 2（小公司/创业），问题 3 选 2（完整立项方案），问题 4 选 1 + 3（文字 + HTML 可视化）。

**Claude**：资料盘点充足 → 路径 B（争取资源框架）。

**执行第四部分前先反问合规**：
> "你的业务有没有数据合规硬性要求？比如用户身份证、银行卡、医疗记录等不能传到第三方？"

**用户**：无硬性合规要求。

**Claude**：联网搜索 DeepSeek-V4-Flash API 和阿里云 ECS 当前价格 → 填入第四部分。

**产出**：完整 5 部分立项方案，重点放在 ROI、回本周期、退出机制。最后用 HTML 可视化呈现 4 层架构图（带 contenteditable 文字 + 下载按钮）。

### 示例 3：场景 3 + 完整立项方案（路径 B，个人/学习版）

**用户**：「我个人想做一个帮自己整理读书笔记的 AI 工具，给自己出一份完整方案算算账。」

**Claude**：触发 skill → 问题 2 选 3（个人/学习），问题 3 选 2（完整立项方案），问题 4 选 1。

**Claude**：资料盘点 = 中等（个人需求清楚但 AI 笔记类工具竞品多）→ 联网搜同类产品（如 Notion AI、Mem.ai 等）的常见架构。

**Claude**：路径 B，**采用自我推演框架**——重点放在技术可行性、自费成本、个人时间投入、是否值得做。

**产出**：5 部分立项方案，但：
- 第一部分写"个人动机"而非"企业现状"
- 第四部分成本用自费视角（"我每月能承受多少 API 钱"）
- 第五部分团队配置简化为"我自己 + 可能的外包"
- 加一节"放弃判断"：什么情况下我应该认识到这不值得继续做
