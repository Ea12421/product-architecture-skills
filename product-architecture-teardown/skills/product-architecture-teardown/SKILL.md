# 产品架构拆解 Skill

## 1. 这个 skill 是什么

帮用户**逆向拆解已有 AI 产品**的整体架构。通过六步反向追问法,把任意产品装进 4 层骨架(数据/能力/场景/触达 + 数据流转)。

适用两种目的(由用户在开场 5 问中选择):
- **深度研究学习**:理解产品的设计意图、取舍逻辑
- **找竞品机会**:识别参考产品的模块强弱、数据沉淀、场景覆盖中的差异化切入点

## 2. 何时触发 / 何时不触发

**何时触发**(明确表达以下意图):
- 想拆解/逆向/分析某个 AI 产品的架构
- 想看懂一个产品由哪些业务模块组成
- 想找参考产品的薄弱环节作为竞品切入点
- 想用六步法或 4 层骨架做产品复盘

**何时不触发**:
- 单纯的功能对比、feature 清单对比
- UI/UX 评测、界面体验评价
- 技术栈分析、技术实现猜测(属于技术架构)
- 商业模式 / 盈利模式分析
- 用户画像 / 市场调研 / 数据分析
- 产品发展史 / 版本迭代分析
- 想搭建自己的新产品(用 `product-architecture-build` skill)

## 3. 核心概念

### 3.1 产品架构是什么

**定义**:产品架构 = 把一个产品拆成几大业务模块 + 说明这些模块如何协作 + 标注数据如何在模块间流转。

不是"这个产品长什么样"(UI),也不是"用什么技术做"(技术架构),而是"由哪几块业务组成、相互怎么搭配、数据从哪进哪出"。

| 视角 | 看到的微信 | 给谁看 |
|------|-----------|--------|
| 信息架构 | 底部 4 个 tab | 交互设计师 |
| **产品架构** ★ | 六大业务模块:IM / 社交 / 内容 / 支付 / 平台 / 企业服务 | 老板和团队 |
| 技术架构 | 分布式 / PaxosStore / 微服务 | CTO / 架构师 |

**本 skill 拆解的就是中间那个。** 如果用户问的其实是别的角度("这产品技术栈是什么" = 技术架构、"界面好看吗" = UI 评测),明确指出后建议用户换问法或换工具。

### 3.2 4 层最小骨架

| 层 | 回答的问题 |
|---|----------|
| 数据层 | 数据/资源从哪来? |
| 能力层 | 拿数据做什么处理? |
| 场景层 | 能力怎么组合成场景? |
| 触达层 | 结果怎么交付给用户? |

原则:
- 层名不固定,固定的是"下层为上层支撑"的分层原则
- 4 层是下限,复杂产品可扩展到 5-6 层
- 必须有跨层数据流转箭头——少了流转就不是架构,是功能清单

### 3.3 数据流转的两种必备类型

每张架构图必须至少包含:
- **沉淀流**:用户行为/对话/上传 → 数据层
- **回补流**:数据层加工后 → 上层

可选追加:跨系统外延流、反向回路流。

### 3.4 推测内容处理原则 ⚠️ teardown 灵魂规则

拆解的价值在"**实证 + 显性假设**"。混淆实证和猜测会让用户基于错误信息做决策。

**任何 Claude 自己推断的内容**(不是用户提供的、也不是搜索到的实证)都必须在文字旁标 `[推测]`。例如:

- "数据层:用户对话历史 + UGC 智能体内容 + `[推测]` 用户行为日志"
- "能力层:豆包大模型 + Seedream + `[推测]` 内容审核模型"

**触发标 `[推测]` 的横切关注点**(整个工作流都要主动标):
- 第四步反推能力时 Claude 自己猜的能力
- 第五步反推数据时 Claude 自己猜的数据来源
- 任何非用户提供 / 非搜索结果的内容

**视觉呈现规则在另一份 reference 里** → 当产出 HTML 含推测内容时,**必读 `references/speculation-markers.md`**(规则见 §8 引用规则表)。

## 4. 工作流

### Step 1:开场 5 问

用纯文字依次询问。如果用户首句已经回答了某个问题,跳过对应问题。

**问题 1:你要拆解哪个产品?** 请说明产品名 + 简要类型。
**问题 2:你的拆解目的是?(单选)**
1. 深度研究学习(理解为什么这样设计)
2. 找竞品机会(识别薄弱模块、差异化切入点)

**问题 3:你想要的深度?(单选,决定路径)**
1. 快速概览(直接出 4 层架构图 + 一段总评,约 5 分钟)
2. 完整方法演示(走完六步法,约 15-30 分钟)

**问题 4:产出形态?(可多选)**
1. 文字结构化说明
2. Mermaid 架构图代码
3. HTML 可视化(带可编辑文字 + 下载按钮)

**问题 5:视觉风格?(仅当问题 4 选了 HTML 时询问;单选)**
1. 技术克制(默认推荐)
2. 暖色友好
3. 极简日式
4. 暗黑赛博

未明确选择默认走 1(技术克制)。具体色板和字体规则见 `references/visual-styles.md`。

### Step 2:资料盘点

判断对**目标产品**信息充足度:

- **充足**:Claude 训练里有这个产品的足够信息 / 用户提供了官网、文档、截图 → 进 Step 3
- **中等**:信息零散 → 调用 web search(若环境支持联网)搜目标产品的官网、博客分析 → 进 Step 3
- **稀缺**:Claude 不熟悉这个产品 + 无联网 + 用户没提供信息 → 进补料分支:

> 我对这个产品了解有限,需要你补充几个具体信息才能可靠拆解:
> 1. 主要用户群是谁?
> 2. 用户可见的核心 3-5 个功能是什么?
> 3. 数据来源大致有哪几类?
> 4. 最常用的 1-2 个场景是什么?

用户拒绝补料 → 明确告知:"当前信息不足以做可靠拆解。"**不要硬出全推测的架构图。**

### Step 3:路径分流

| 问题 3 | 路径 |
|---|---|
| 1(快速概览) | 路径 A:5 分钟版 |
| 2(完整方法演示) | 路径 B:完整六步法 |

### 路径 A:快速概览版

直接出结果,跳过六步法详细演示:

1. **4 层架构图**(含至少 1 条沉淀流 + 1 条回补流)
2. **每层的核心模块**(写主干,不细分子模块)
3. **一段总评**(按问题 2 调整):
   - 深度研究 → 写"设计意图和取舍逻辑"
   - 找竞品机会 → 写"模块强弱 + 至少 2 个差异化切入点"

### 路径 B:完整六步法

把六步逐一展示,每步都有阶段产出。

| 步骤 | 内容 | 阶段产出 |
|---|---|---|
| **第一步:体验** | 不强求亲身使用,通过官网/介绍/截图/web search/用户描述"**获取足够功能感知**" | 5-10 句话描述"用户能干什么" |
| **第二步:穷举** | 穷举所有用户可见功能,不放过角落功能 | 分组列出所有功能 |
| **第三步:归类** | 用"砍掉 A,B 是否受影响"测试合并成业务模块。**粒度原则**:归到"功能帮用户做什么事"就够了,不需要按钮位置和 UI 文案——那是信息架构 | 4-6 个业务模块表 |
| **第四步:反推能力** | 每个模块需要什么底层能力? | 5-10 个核心能力。Claude 自己推测的标 `[推测]` |
| **第五步:反推数据** | 每个能力依赖什么数据? | 数据来源清单。推测的标 `[推测]` |
| **第六步:画图** | 汇总前 5 步,画 4 层架构图,**必含数据流转箭头** | 按问题 4 选定形态产出 |

第六步之后加总评(按问题 2 调整,同路径 A)。

## 5. 强制规则

1. **推测内容必须标 `[推测]`**:见 §3.4 推测内容处理原则。任何 Claude 推断的内容都要标。
2. **数据流转必须有**:至少 1 条沉淀流 + 1 条回补流。实在想不到回路时明确告知"当前观察到的功能里没看到回补设计"。**不允许跳过。**
3. **4 层是起点不是终点**:平台型加生态层 / 多 Agent 型分工具层 / ToB 加安全层。底线不少于 4 层。
4. **按目的差异化产出**:问题 2 答案影响最后总评的写法(见六步法第六步 / 路径 A 第 3 项)。

## 6. 跨 skill 协作 + 中途偏离 + 收尾

### 检测「想自己搭一个」时的反问

用户说「我也想做」「自己搭一个」「基于这个我要…」等,先反问:

> "拆完想自己搭一个吗?"

- 选不搭 → 继续当前 skill 完成拆解
- 选要搭 → 提示:"建议拆解完成后用 `product-architecture-build` skill 开始搭你自己的产品架构。"

### 中途偏离

用户切换话题时:
1. 识别偏离
2. 总结当前进度:"我们暂停在 [当前步骤]。已收集:[列已确认项]。要切换是吧?"
3. 干净交接,等确认后退出 skill
4. 保留 2-3 行摘要,方便用户续接

### 收尾行为

| 情况 | 行为 |
|---|---|
| 完整产出 | 直接结束,不追加 |
| 多处 `[推测]` 标记 | 追加:"产出中带 [推测] 标记的部分基于公开信息和推测。如果之后拿到内部资料或更多数据想完善,把信息贴给我即可重跑。" |
| 中途叫停 | 追加:"我们暂停在 [XX 步骤],已收集:……。要继续时把这段贴回来就能接着跑。" |

## 7. 产出形态

按问题 4 的多选结果产出。

### 文字结构化说明(默认)

按 4 层骨架逐层说明,最后写"数据流转"独立小节。`[推测]` 标记保留在文字里。

### Mermaid 架构图代码

用 `graph TB` 画分层,`subgraph` 圈每层。⚠️ Mermaid 对"分层堆叠 + 跨层箭头"的可视化表现一般,节点多时容易乱。视觉要求高建议同时选 HTML。

### HTML 可视化(带可编辑文字 + 下载按钮)

⚠️ **如果用户选了 HTML 输出,立即按 §8 引用规则表的顺序读 references**:
1. **先读** `references/visual-styles.md`(决定色板和字体)
2. **再读** `references/html-spec.md`(布局 / 工具栏 / 模块 / 缩放 / 可编辑 / 下载)
3. **画箭头前读** `references/arrow-routing.md`(间隙列路由 + 垂直起终点 + 添加/删除交互)
4. **渲染含 `[推测]` 内容前读** `references/speculation-markers.md`(三重视觉区分 + 虚线箭头)

每读完一份 reference,在产出前用一句话向自己确认"已阅读 X.md,关键约束是 Y"——见 §8 自我确认机制。

## 8. ⚠️ 引用规则(必须遵守)

下面每条规则在触发条件成立时**必须**先读对应 reference,再继续产出。**不读直接产出 = 错误产出。**

| 触发条件 | 必读 reference | 读取时机 |
|---|---|---|
| Q4 选择了 HTML 输出 | `references/visual-styles.md` | 决定色板和字体之前 |
| Q4 选了 HTML(visual-styles.md 已读) | `references/html-spec.md` | 写任何 HTML/CSS 之前 |
| 画自动箭头 / 处理「添加连接」/「删除箭头」 | `references/arrow-routing.md` | 写任何 SVG path 之前 |
| 渲染含 `[推测]` 内容(teardown 专属) | `references/speculation-markers.md` | 渲染推测元素之前 |

**自我确认机制**:读完每份 reference,在产出前用一句话向自己确认:
> "已阅读 [文件名],关键约束是 [一句话总结]。"

未做自我确认 = 视为未读,必须重读。

## 9. 通用自检(产出前过一遍)

- [ ] 已按问题 3 的选择走对路径(A 快速概览 / B 完整六步法)
- [ ] 有至少 1 条沉淀流 + 1 条回补流(或明确告知缺失原因)
- [ ] 推测内容都标了 `[推测]`,没有把猜测当事实写
- [ ] 最后总评按问题 2 的目的调整了侧重
- [ ] 用户拒绝补料时没有硬出全推测的架构图
- [ ] 涉及具体定价时(成本估算等)用了 web search 或明确告知用户自查
- [ ] 没把 UI 评测 / 技术栈猜测 / 商业模式分析硬塞进产出
- [ ] HTML 产出时引用规则表里相关 reference 都读了 + 做了自我确认

> ⚠️ HTML 专项自检(工具栏 fixed、间隙列路由、可编辑、下载等)在 `references/html-spec.md` 和 `references/arrow-routing.md` 各自的自检节里,不在主 SKILL.md 重复。

## 10. 示例

### 示例 1:快速概览(路径 A,深度研究目的)

**用户**:「拆一下豆包,我想快速看看它的产品架构。」

**Claude**:开场 5 问(问题 1 已答)→ Q2 选 1(深度研究)→ Q3 选 1(快速概览)→ Q4 选 1 + 2(文字 + Mermaid)。资料充足 → 路径 A。

**产出**:4 层架构图 + 每层主干模块 + 沉淀流和回补流 + 总评(写"对话引擎为核心 + 多模态延伸 + 智能体开放"的设计逻辑;Coze 框架开放给用户做 UGC 智能体是把工具变平台的关键一步)。

### 示例 2:完整六步法(路径 B,找竞品机会目的)

**用户**:「拆一下 Mem.ai 找差异化机会,完整六步法走一遍。」

**Claude**:Q2 选 2(找竞品机会)→ Q3 选 2(完整六步法)→ Q4 选 1 + 3(文字 + HTML)→ Q5 选 1。资料中等 → web search 补料。

**Claude**:
- 触发 HTML → **立即读** visual-styles.md / html-spec.md / arrow-routing.md → 第六步出 HTML 时**还要读** speculation-markers.md(因为四五步多处 `[推测]`)
- 按六步演示,第四步识别 `[推测]` 推荐算法,第五步识别 `[推测]` Embedding 向量库
- 总评:**薄弱模块**(协作能力弱)+ **数据沉淀缺口**(没把笔记结构化提取知识图谱)+ **场景覆盖空白**(无会议笔记+行动项追踪)→ 至少 2 个差异化切入点
