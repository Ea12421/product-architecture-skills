# 产品架构拆解 Skill

## 1. 这个 skill 是什么

帮用户**逆向拆解已有 AI 产品**的整体架构。通过六步反向追问法，把任意产品装进 4 层骨架(数据/能力/场景/触达 + 数据流转)。

适用两种目的（由用户在开场 4 问中选择）：
- **深度研究学习**：理解产品的设计意图、取舍逻辑
- **找竞品机会**：识别参考产品的模块强弱、数据沉淀、场景覆盖中的差异化切入点

## 2. 何时触发

仅在用户明确表达以下意图时启动：
- 想拆解/逆向/分析某个 AI 产品的架构
- 想看懂一个产品由哪些业务模块组成
- 想找参考产品的薄弱环节作为竞品切入点
- 想用六步法或 4 层骨架做产品复盘

## 3. 何时不触发

下列场景不要触发这个 skill：
- 单纯的功能对比、feature 清单对比
- UI/UX 评测、界面体验评价
- 技术栈分析、技术实现猜测（属于技术架构）
- 商业模式 / 盈利模式分析
- 用户画像 / 市场调研 / 数据分析
- 产品发展史 / 版本迭代分析
- 想搭建自己的新产品（用 product-architecture-build skill）

## 4. 核心概念

### 4.1 产品架构是什么

**定义**：产品架构 = 把一个产品拆成几大业务模块 + 说明这些模块如何协作 + 标注数据如何在模块间流转。

简单说：不是"这个产品长什么样"（那是 UI），也不是"这个产品用什么技术做"（那是技术架构），而是"这个产品由哪几块业务组成、相互怎么搭配、数据从哪进哪出"。

**举个例子（微信）**：

| 视角 | 看到的微信 | 给谁看 |
|------|-----------|--------|
| 信息架构 | 底部 4 个 tab：消息 / 通讯录 / 发现 / 我 | 交互设计师 |
| **产品架构** ★ | 六大业务模块：IM 通讯 / 社交网络 / 内容生态 / 金融支付 / 平台生态 / 企业服务（+ 底层：账号体系 / 关系链 / 消息系统） | 老板和团队 |
| 技术架构 | 分布式系统 / PaxosStore / 微服务 / Raft 协议 | CTO / 架构师 |

**本 skill 拆解的就是中间那个产品架构。**

### 4.1.1 别和其他架构搞混

| 架构类型 | 回答什么问题 | 谁主导 |
|---------|------------|--------|
| 信息架构 | 用户看到什么？页面怎么组织？导航怎么分级？ | 产品/交互设计师 |
| **产品架构** ★ | 产品由哪几块业务组成？模块间怎么协作？数据怎么流转？ | **产品经理（本 skill 拆解的就是这个）** |
| 技术架构 | 系统怎么实现？技术栈？部署？ | CTO / 架构师 |

如果用户问的其实是别的角度（"这产品技术栈是什么" = 技术架构、"界面好看吗" = UI 评测），明确指出后建议用户换问法或换工具，不要在产品架构 skill 里硬塞。

### 4.2 4 层最小骨架

从下往上：

| 层 | 回答的问题 | 内容 |
|---|----------|------|
| 数据层 | 数据/资源从哪来？ | 用户数据、知识库、第三方接入等 |
| 能力层 | 拿数据做什么处理？ | 大模型、RAG、推理、生成 |
| 场景层 | 能力怎么组合成场景？ | 把能力封装成具体业务场景 |
| 触达层 | 结果怎么交付给用户？ | App、Web、小程序、API 等 |

原则：
- 层名不固定，固定的是"下层为上层支撑"的分层原则
- 4 层是下限，复杂产品可扩展到 5-6 层
- 必须有跨层数据流转箭头——少了流转就不是架构，是功能清单

### 4.3 数据流转的两种必备类型

每张架构图必须至少包含：
- **沉淀流**：用户行为/对话/上传 → 数据层
- **回补流**：数据层加工后 → 上层

可选追加：跨系统外延流、反向回路流。

## 5. 工作流

### Step 1：开场 4 问

用纯文字依次询问。如果用户首句已经回答了某个问题，跳过对应问题。

**问题 1：你要拆解哪个产品？**
请说明产品名 + 简要类型。例如：
- "豆包，AI ToC 对话助手"
- "Mem.ai，AI 笔记产品"
- "我们公司的内部某 ToB 智能体系统"

**问题 2：你的拆解目的是？（单选，决定产出侧重）**
1. 深度研究学习（理解为什么这样设计、取舍逻辑）
2. 找竞品机会（识别薄弱模块、数据沉淀缺口、场景覆盖空白）

**问题 3：你想要的深度？（单选，决定路径）**
1. 快速概览（直接出 4 层架构图 + 一段总评，约 5 分钟）
2. 完整方法演示（走完六步法：体验 → 穷举 → 归类 → 反推能力 → 反推数据 → 画图，过程更长但能学到方法，约 15-30 分钟）

**问题 4：产出形态？（可多选）**
1. 文字结构化说明
2. Mermaid 架构图代码
3. HTML 可视化（带可编辑文字 + 下载按钮）

**问题 5：视觉风格？（仅当问题 4 选了 HTML 时询问；单选）**
1. **技术克制（默认推荐）**—— Linear / Vercel 风，深底冷色调，适合给老板和团队看
2. **暖色友好**—— Notion / Stripe 风，亮底暖色调，适合面向用户的产品介绍
3. **极简日式**—— Apple / 无印良品风，留白多 + 单一强调色，追求精致感
4. **暗黑赛博**—— 科幻游戏 UI 风，深底霓虹色，适合 AI / 科技概念项目

如果用户没明确选，默认走 1（技术克制）。

### Step 2：资料盘点

判断手头对**目标产品**的信息充足度：

- **充足**：Claude 训练里有这个产品的足够信息 / 用户提供了官网、文档、截图 → 进 Step 3
- **中等**：信息零散 → 调用 web search（若环境支持联网）搜目标产品的官网、产品介绍、博客分析文章 → 进 Step 3
- **稀缺**：Claude 不熟悉这个产品 + 无联网 + 用户没提供信息（典型场景：内部产品、新发布产品、冷门垂直工具） → 进"补料分支"：

  > 我对这个产品了解有限，需要你补充几个具体信息才能可靠拆解：
  > 1. 这个产品的主要用户群是谁？
  > 2. 用户可见的核心 3-5 个功能是什么？
  > 3. 数据来源大致有哪几类？（用户上传？联网搜？知识库？）
  > 4. 用户最常用的 1-2 个场景是什么？

  用户补完信息后再进 Step 3。如果用户拒绝补料，明确告知："当前信息不足以做可靠拆解。建议你先收集产品官网/介绍/截图等资料再来，或者把上面 4 个问题答一下我就能继续。" **不要硬出一个全是猜测的架构图。**

### Step 3：路径分流

根据问题 3 的答案：

| 问题 3 | 路径 |
|--------|------|
| 1（快速概览） | 路径 A：5 分钟版 |
| 2（完整方法演示） | 路径 B：完整六步法 |

### 路径 A：快速概览版

跳过六步法的详细演示，**直接出结果**：

1. 4 层架构图（含至少 1 条沉淀流 + 1 条回补流）
2. 每层的核心模块（不细分子模块，写主干即可）
3. 一段总评（**根据问题 2 调整侧重**）：
   - 深度研究目的 → 总评写"这个产品的设计意图和取舍逻辑"
   - 找竞品机会目的 → 总评写"模块强弱判断 + 至少 2 个差异化切入点"

按问题 4 选定的产出形态呈现。

### 路径 B：完整六步法

把六步逐一展示，每步都有阶段产出，让用户能看到方法本身。

#### 第一步：体验

⚠️ 原方法里这一步是"完整走一遍核心功能"，但实际很多产品没法直接体验（ToB 内部系统、付费产品、已下线产品、闭源产品等）。

本 skill **放宽定义**：第一步不强求亲身使用，而是"**获取足够的功能感知**"，渠道可包括：
- 用户描述
- 官网 / 产品介绍页 / 文档
- web search 找到的介绍文章、博客分析、用户评测
- 用户提供的截图

阶段产出：列出 5-10 句话描述这个产品的"用户能干什么"。

#### 第二步：穷举

**穷举所有用户可见的功能**。不放过任何角落功能，漏掉一个可能就漏掉一整个业务模块。

阶段产出：分组列出所有功能（按"对话类 / 输入类 / 生成类 / 工具类"等粗略分组）。

#### 第三步：归类

**用"砍掉 A，B 是否受影响"的测试**，把功能合并成业务模块：
- **互不影响** → 并列模块，可拆分到不同模块
- **有依赖** → 同一模块或上下层关系

**粒度原则**：归类到"这个功能能帮用户做什么事"就够了，**不需要**记按钮位置、交互细节、UI 文案——那些是信息架构的事，不是产品架构。

阶段产出：表格列出 4-6 个业务模块，每个模块包含哪些功能、核心价值是什么。

#### 第四步：反推能力

每个业务模块需要什么底层能力？

阶段产出：列出 5-10 个核心能力（大模型对话、RAG、ASR/TTS、图片生成、文档解析、智能体框架等）。Claude 推测的能力必须标 `[推测]`。

#### 第五步：反推数据

每个能力依赖什么数据？

阶段产出：列出数据来源（用户行为、用户上传文件、互联网数据、UGC 内容、知识库等）。Claude 推测的数据来源必须标 `[推测]`。

#### 第六步：画图

汇总前 5 步，画出 4 层架构图，必须包含数据流转箭头（沉淀流 + 回补流，可选追加跨系统外延流）。

按问题 4 选定的产出形态呈现。

最后加一段总评（**根据问题 2 调整**）：
- 深度研究 → "设计意图：为什么这样分层、为什么这些模块、数据流为什么这样设计"
- 找竞品机会 → "薄弱模块 + 数据沉淀缺口 + 场景覆盖空白 + 至少 2 个差异化切入点"

## 6. 强制规则

### 规则 1：推测内容必须标 `[推测]`

整个拆解过程中，**任何 Claude 自己推断的内容**（不是用户提供的、也不是搜索到的实证）都必须在文字旁标 `[推测]`。例如：

- "数据层：用户对话历史 + UGC 智能体内容 + 联网搜索数据 + `[推测]` 用户行为日志"
- "能力层：豆包大模型 + Seedream 图片生成 + `[推测]` 内容审核模型"

为什么强制：拆解的价值在"实证 + 显性假设"。混淆实证和猜测会让用户基于错误信息做决策。

### 规则 2：数据流转必须有

任何架构图必须至少包含：
- 1 条沉淀流（用户行为 → 数据层）
- 1 条回补流（数据层 → 上层）

实在想不到回路时明确告知："当前观察到的功能里没看到回补设计，可能产品自身就缺这个环节（也可能是观察不全）。" **不允许跳过。**

### 规则 3：4 层是起点不是终点

默认 4 层，但允许扩展：
- 平台/marketplace 型 → 加生态层
- 多 Agent 协同型 → 能力层内部分"工具层 / Agent 编排层"
- ToB 企业级 → 加纵向贯穿的"安全/权限层"

底线：不能少于 4 层。

### 规则 4：按目的差异化产出

问题 2 的答案影响**最后那段总评的写法**：

| 问题 2 答案 | 总评的侧重 |
|------------|----------|
| 深度研究学习 | 写"为什么这样设计"——分层逻辑、模块取舍、数据回路的设计意图 |
| 找竞品机会 | 写"机会窗口"——哪个模块薄弱、哪类数据没沉淀、哪类场景没覆盖、至少 2 个差异化切入点 |

## 7. 跨 skill 协作

### 检测「想自己搭一个」时的反问

如果用户的话里出现「我也想做」「自己搭一个」「基于这个我要…」「这个产品我能不能复刻」等词，先反问：

> "拆完想自己搭一个吗？"

- 选不搭 → 继续当前 skill 完成拆解
- 选要搭 → 提示：
  > "建议拆解完成后用 product-architecture-build skill 开始搭你自己的产品架构。如果你没装 build skill，告诉我你的搭建目标，我可以基于刚才的拆解结果直接给你一个搭建建议。"

## 8. 中途偏离处理

如果用户在工作流中途切换话题（比如六步法走到第三步突然说"等等，先帮我看个文档"），按以下流程：

1. **识别偏离**：用户的话和当前 skill 工作流明显无关
2. **总结当前进度**：
   > "我们暂停在 [当前步骤]。已收集的信息：[列出已确认的项]。要切换是吧？"
3. **干净交接**：等用户确认切换后退出 skill，让 Claude 处理新方向
4. **保留摘要**：退出前把已收集的信息整理成 2-3 行摘要，方便用户之后续接

不要强制要求用户完成 skill 后再切换。

## 9. 收尾行为

根据情况决定是否追加：

| 情况 | 行为 |
|------|------|
| 完整产出（信息齐全、按路径走完） | 直接结束，不追加 |
| 带较多假设的部分产出（多处 `[推测]` 标记） | 追加："产出中带 [推测] 标记的部分是基于公开信息和推测。如果之后你拿到内部资料或更多数据想完善，把信息贴给我即可重跑。" |
| 中途叫停 | 追加："我们暂停在 [XX 步骤]，已收集的信息：……。要继续时把这段贴回来就能接着跑。" |

## 10. 产出形态

按问题 4 的多选结果产出。多选时按以下顺序：

### 文字结构化说明（默认）

按 4 层骨架逐层说明，最后写"数据流转"独立小节列出所有流转方向和内容。`[推测]` 标记保留在文字里。

### Mermaid 架构图代码

用 `graph TB` 画分层，`subgraph` 圈每层，节点写内容，箭头标流转方向和文字标签。

⚠️ Mermaid 对"分层堆叠 + 跨层箭头"的可视化表现一般，节点多时容易乱。如果用户对视觉效果要求高，建议同时选 HTML 可视化。

### HTML 可视化（带可编辑文字 + 下载按钮）

产出一段完整的、独立可运行的 HTML 代码。

#### 视觉基线（按问题 5 选的风格执行）

**不要**用 Tailwind 默认灰白圆角风格。按用户选的风格执行：

**风格 1：技术克制（默认）—— Linear / Vercel 风**
- 背景 `#0F172A`（深蓝黑），主文字 `#F8FAFC`
- 4 层冷色调：数据 `#3B82F6`（冷蓝）/ 能力 `#8B5CF6`（紫）/ 场景 `#06B6D4`（青）/ 触达 `#A78BFA`（淡紫）
- 圆角 8px，字体 Inter + PingFang SC

**风格 2：暖色友好—— Notion / Stripe 风**
- 背景 `#FEFBF6`（暖米白），主文字 `#1F2937`
- 4 层暖色调：数据 `#F97316`（橙）/ 能力 `#EAB308`（金）/ 场景 `#EC4899`（粉红）/ 触达 `#A855F7`（淡紫）
- 圆角 12px，字体 DM Sans + 思源黑体

**风格 3：极简日式—— Apple / 无印良品风**
- 背景 `#FAFAFA`（近白），主文字 `#1A1A1A`
- 4 层同色相不同明度灰阶：`#2D2D2D` / `#525252` / `#737373` / `#A3A3A3`
- 单一强调色 `#DC2626`（点缀红，仅用于数据流转箭头）
- 圆角 4px，衬线字体 Noto Serif JP + 思源宋体

**风格 4：暗黑赛博—— 科幻游戏 UI 风**
- 背景 `#000000`（纯黑）+ 网格底纹，主文字 `#00FFFF`（青）
- 4 层霓虹色：数据 `#FF00FF`（品红）/ 能力 `#00FF00`（亮绿）/ 场景 `#FFFF00`（黄）/ 触达 `#FF0080`（粉红）
- 所有色块加 `box-shadow: 0 0 20px` 自身颜色的发光
- 圆角 0px（直角），等宽字体 JetBrains Mono + 思源等宽

#### `[推测]` 标签可视化（拆解 skill 专用）

无论选哪种风格，推测内容**必须**视觉上和实证内容明显区分：

- **容器**：1px dashed 虚线边框（不是实线），颜色比所在层主色浅 30%
- **文字**：`font-style: italic`（斜体）
- **文字色**：比实证内容浅一档（如主文字 `#F8FAFC` → 推测 `#94A3B8`）
- **三重区分**（虚线 + 斜体 + 浅色）叠加使用，让用户一眼分清推测和实证，避免误信猜测内容

#### 通用视觉原则（所有风格共用）

- **字体**：font-family 链中英结合，英文 fallback 中文（例如 `"Inter", "PingFang SC", sans-serif`），让英文有专门字体不被中文字体挤压
- **字号层级**：层名 ≥ 18px / font-weight 600，模块名 ≥ 14px / 500，数据流转标签 ≥ 12px
- **密度**：层之间间距 24-32px，层内模块间距 12-16px
- **布局**:4 层堆叠（CSS Grid 或 Flexbox），自下而上：数据 → 能力 → 场景 → 触达
- **数据流转箭头**：用 SVG 曲线（不用直线，太工程化），箭头本体颜色用中性灰 `#94A3B8`（赛博风用 `#FF00FF`），标签字号 ≥ 12px，背景加半透明色块衬底
- **对比度**：主要文字对所在背景 ≥ 7:1（极简日式至少 4.5:1）

#### 与 web-design skill 协作（可选）

如果检测到项目里已存在 `DESIGN.md`（通常是 web-design skill 的产物），**优先读取**里面的色板/字体/密度 token 替换上面的视觉基线，让架构图视觉和项目其他页面统一。

DESIGN.md 不存在时按选定风格的基线产出，**不要**主动要求用户先去用 web-design skill —— 产品架构拆解不应该被视觉决策卡住。

#### 可编辑要求

- 所有文字元素加 `contenteditable="true"` 属性：层名、模块名、数据流转标签都可以在浏览器里直接点击编辑
- 文字元素 hover 时给一个浅色背景提示用户可编辑
- 编辑只在浏览器里临时生效，关闭页面会丢失（除非用下载按钮）

#### 下载按钮要求

- 页面顶部或角落**固定**（position: fixed）一个「下载修改后版本」按钮，滚动时仍可见
- 用户编辑后点击 → JavaScript 用 Blob + URL.createObjectURL 把当前 DOM 序列化成 HTML 字符串 → 触发浏览器下载完整的 .html 文件
- 文件名格式：`产品架构拆解_[产品名]_[时间戳].html`

#### 适配两种环境

- 在 claude.ai 里：作为 artifact 渲染，用户直接编辑、点下载按钮即可
- 在 Claude Code / Codex 等环境里：把完整 HTML 代码贴给用户，告诉用户"保存为 .html 文件后用浏览器打开即可编辑和下载"

#### 质量自检（产出前过一遍）

- [ ] 4 层颜色明显区分，没有"两层颜色太接近看不出来"
- [ ] 数据流转箭头视觉清晰，不被其他元素遮挡
- [ ] 字号有层级（层名 > 模块名 > 标签）
- [ ] 主要文字对比度达标
- [ ] **推测内容**用虚线 + 斜体 + 浅色标注，和实证明显区分
- [ ] hover 时编辑提示明显
- [ ] 下载按钮 position: fixed，滚动时仍可见
- [ ] 没用 Tailwind 默认灰白卡片风格（除非用户明确要求）

### 示例 2：完整六步法（路径 B，找竞品机会目的）

**用户**：「我想拆一下 Mem.ai 这个 AI 笔记产品，找一下做自己产品的差异化机会。完整六步法走一遍。」

**Claude**：资料盘点 = 中等 → 联网搜 Mem.ai 官网 + 评测博客。

**Claude**：路径 B，按六步逐步演示：

- **第一步 体验**：通过官网和评测了解到 Mem.ai 的核心是"AI 自动整理笔记 + 跨笔记联想 + 自然语言对话查询"
- **第二步 穷举**：列出 12 个用户可见功能（笔记编辑器 / AI 总结 / AI 联想 / 跨笔记搜索 / 对话查询 / 模板 / 协作 / 分享 / 移动端同步 / 离线 / 导入 / 导出）
- **第三步 归类**：用"砍掉 A 影响 B 吗"测试合并成 5 个业务模块
- **第四步 反推能力**：识别出大模型对话、Embedding 检索、自动摘要、笔记结构化 + `[推测]` 推荐算法
